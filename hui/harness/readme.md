# Harness Engineering

## 从概念层面，掌握harness engineering
  ###  最基础的意思
  - 名词 马的护具/安全带/背带/牵引装置
  - 动词 
  harness something=把某种能力资源“用起来，为我所用”
  比如：harness Ai 利用AI
  harness energy 利用能源 （可控核聚变）
  本质不是用，而是
  把原本不受控的东西， 变成可控工具

### AI 编程语境下
Harness = 驾驭模型/控制系统

Harness Engineering 关注的就是如何给Ai Agent 设计一套可以稳定工作的一个控制系统。
Harness 可以理解为 Agent搭的一套配套的一个工作装备（控制系统）， 比如工作的规则， 产品的文档，架构的文档，验收标准，以及一些交接的记录（下一轮如何继续）
它的目标是让Agent 所需要的一些信息，流程变成能看懂，能执行能验证的一个系统的能力。
不是让模型变得更聪明，而是让环境更适合Agent来执行。

在同一个模型下， 同一份项目， 如果增加了一定的harness 之后， 即使是同一个模型， 它开发的正确率会有翻倍的提升。

## 发展史
  ### 2026年为什么大家讲harness？
  - AI 能力变强了
  Ai Agent 从最开始是提示词，AI问答助手，现在可以完成一个复杂的一个开发任务。
  - 任务性质发生改变
  AI Agent变强后， 人的工作性质发生改变， 
  我们不止让Agent做事， 而是让它在做事的过程中，变得稳定可控可验证，做完一轮， 还可以做下一轮。
  - 核心问题改变
  如何让Agent稳定可控可验证，可交接的执行

  光靠一段Prompt 和足够的上下文就已经不够了，这就是Harness 变得重要的原因。

  ### Prompt 仍然很重要
  harness 不是来替代我们的Prompt的，而是建立在Prompt之上的新方法。

  - 提示词能做什么？
  依旧能够帮我们把任务说清楚，完成什么目标，用什么技术栈， 输出什么格式，遵循哪些约束。
  练习打磨自己的提示词和训练写提示词的能力

  ### Harness的定位
  面对更复杂的开发任务， 光靠一段Prompt 不够的，  Harness是建立在Prompt 之上的 方法， 两者互相叠加。

  ### AI 编程的3个阶段
  - Prompt Enginnerring
  写提示词，把任务说清楚。
  关注点：怎么告诉AI 需求，让AI更好地执行
  适合场景：单词任务，短周期问题， 明确的局部修改， 提升单次沟通质量。
  - Context Enginnering 
  让Ai看见必要信息
  关注点： AI 在行动前应该看到哪些上下文， 
  包括项目文档， 代码文件， 错误日志， 测试结果
  核心变化： 从怎么问 变成 让Ai 看见什么

  - Harness Enginnering 
  受控环境里继续干活
  关注点：如何让Ai 在受控的环境里持续完成复杂任务， 不只提供信息， 还要提供工作流程。
  包含： 规则、边界、验证、工具、交接、反馈机制。

真正做项目的时候， 这三者都会一起使用的。 

### 阶段1 Prompt Engineering
- 和Ai说明白需求
- 输出一个怎样的格式
- 最早的时候， 甚至会让AI扮演一个角色

任务越长的时候， 聊天的信息越容易被丢失，或者被误解。因为Context是有限的， 只靠Prompt, 很难承载你的完整的一个工程记忆。

- Context Engineering 
AI在行动之前， 需要给到AI足够的上下文。它就不需要去更具你的提示词来猜你的意图了， 它会去自己阅读文档， 结合阅读代码， 加深对整个项目的一个理解。 包括设定一定的规则。 
Agents.md, Claude.md
- Harness Engineering
让Agent 更稳定地完成真实开发任务， 这些问题靠一段Prompt 很难长期稳定解决， 需要系统化的控制结构。

Prompt Enginneering,是让Ai 听懂并执行你的需求， Context Engineering 看到足够的项目信息， harness是让AI 在一个受控的环境里面持续地去干活。

  这是harness 核心思想。

  ### AGENTS.md/CLAUDE.md
  AGENTS.md 是跨工具通用标准（Codex / Cursor / Copilot / Gemini CLI）；CLAUDE.md 是 Anthropic 自家标准。

  OPENAI 尝试写了一份超长的一个AGENTS.md 这样是错误的， 你不应该把AGENTS.md 写成百科全书， 而应该是一个内容的目录， 
  索引 docs

  如果AI经常忘记需求，可以把需求沉淀到文档
  把需求写进PRODUCT.md ,让Agent每次都能读到。

  AI经常改错方向， 补充架构边界
  在ARCHITECTURE.md 里明确说明哪些技术和模式不能用。 

  补充验收的标准，
  你的项目支持了国际化的处理， 那每次在开发完一个前端页面的时候， 可能需要去增加几个国际化语言的验收， 这个需要在你的AGENTS.md 文档里说明。  

## 实战
  最小的Harness Engineering 
  驱动我们的Agent 去完成一个本地项目的看板。

  - 使用项目模版
    标准nextjs 官方模版项目
    初始化了基础Harness 工程的四分文件
    - AGENTS.md 工作规则
    开始工作前，阅读三份文件， 遇到需求变化怎么处理， 不确实时要先问用户， 每轮更新后要更新交接文件。
    - docs/PRODUCT.md
    产品说明， 这个产品是什么， 给谁用， 
    第一版要做什么， 不做什么。
    - docs/ ARCHITECTURE.md
    技术说明、文件组织、数据模型、本地数据库保存、Agent API 协作方式
    - session-handoff.md
    交接清单。记录未完成事项， 已完成事项、尚未验证的功能， 下一步， 让下一轮Agent能接着做。 

    这4个文件， 构成了最小的控制系统， 让Agent 在开始写代码之前， 先知道规则、目标、架构和当前进度。

    
  - 安装依赖，并跑起来

  本地项目的Agent 管理看板
  具备一定Agent能力的项目， 感受AI开发，不只是写Prompt和硬塞文档了。
  2026年， 最好的做法是给Agent 做好产品的说明， 架构的边界， 工作的规则和一些交接记录。
