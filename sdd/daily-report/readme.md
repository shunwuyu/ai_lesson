# 智能日报生成器

- 编写 proposal.md 文件
- 这份规范写的够不够完善？
  要素都齐备了 背景、目标、功能范围、技术约束及验收标准
  特别是验收标准采用了Checklist 形式， 每一条都具备可测试性
- 容易忽略的关键点
  ① "不做什么"比"做什么"更重要
  如果你不写"不做智能摘要"，AI可能会自作主张：
  "我发现可以加一个LLM总结功能，让日报更智能！"
  → 引入了LLM API依赖、增加了成本、超出了范围
  → "不做"是给AI画的红线
 
  ② 性能验收必须有数字
  "生成速度要快" → AI不知道多快算快
  "生成耗时<60s" → AI知道需要做哪些优化
  没有数字的性能要求 = 没有性能要求
 
  ③ 边界场景是bug的重灾区
  "今天没有提交怎么办？"
  "API挂了怎么办？"
  "周末要不要生成？"
  你不写，AI就猜——猜错了就是生产环境的bug
- 过渡规范与规范不足
  完成第一份 proposal.md 后， 会自我狐疑：“我感觉这份规范还不够细致，例如，邮件标题的格式如何设置、日报各部分该用几级 Markdown 标题、飞书消息的过滤关键词如何配置……这些细节需要补充进去吗？”
 
  这正是初学者在实践 SDD 时常有的困惑：规范的颗粒度究竟该如何把握？

  规范不足， AI 幻觉/执行偏差的风险
  规范过渡  规范编写的成本接近代码编写成本

  表4-1 proposal.md 的内容边界：什么该写，什么不该写
 
  |该写（What）| 不该写（How） |
  |---        |-------------------------------------- |
  | 数据源：|GitHub+飞书 |使用哪个 Python 库调用 GitHub API |
  | 输出格式：|Markdown+HTML | 邮件 HTML 模板的具体 CSS 样式代码 |
  | 性能要求：|执行时间 <60s | 使用多线程还是 asyncio 进行并发处理 |
  | 推送方式：|邮件 + 飞书机器人 |SMTP 配置的具体参数格式 |
  | 功能边界：|不做智能摘要 — |
  | 异常处理边界：|API 超时重试 3 次 | 重试的退避策略（指数退避或固定间隔退避） |


proposal.md 应当涵盖的核心内容——关键决策与约束，而右列则是 proposal.md 不应涉足的内容——具体的实现细节。这些实现细节，若涉及架构层面的抉择，应在 design.md 中予以明确；若仅为编码层面的细枝末节，则可交由 AI 自行处理。
 
小雪由此总结出一条简洁而精准的判断法则：“若一项决策会改变你对系统本身的理解，就应将其写入规范；若一项决策仅影响代码的书写方式，且不改变系统的最终行为，则可放心交给 AI。”


### 4.5 用 Claude Code 辅助编写规范
 
编写规范本身同样可以借助 AI 的力量。但关键在于——**AI应作为你思考的辅助，而非替你做出决策。**
 
一种常见的误用是直接要求 AI：“帮我写一份智能日报生成器的需求文档。” 这样 AI 生成的规范虽然看似完整，实则充满了它基于自身假设所生成的“幻觉”。更优的策略是利用 AI 来引导你进行结构化思考。
 
在 Claude Code 中，你可以通过 CLAUDE.md 加载规范模板，再通过对话逐步完善。以下是一个推荐的 AI 辅助规范编写工作流。
 
图4-5所示工作流的核心在于 Step 3——AI应当负责提出问题，而非擅自作答。当 AI 询问“推送方式是什么”时，它实际上是在协助你识别一个可能被遗漏的决策点。这种方式远优于 AI 默默假设“就用邮件吧”——因为你的真实需求或许是飞书机器人，抑或两者兼具。
 
在试用这套流程后，小冰感慨道：“原来编写规范并非必须从零开始。AI 提供的模板框架与追问引导，能有效帮助我梳理思路。但最终的决策权——无论是选定数据源、明确汇报对象，还是界定完成标准——始终牢牢掌握在我自己手中。”

“这正是 SDD 模式下人机协作的理想分工。”咖哥总结道，“人类负责确立意图与关键决策，AI 负责结构化梳理与执行。这一分工原则贯穿于 SDD 的全流程——从需求分析到架构设计，再到代码实现，无一例外。”

### 4.6 规范质量检测清单

在完成 proposal.md 撰写后，提交至 Git 前，请对照表4-2进行一次自检。
 
表4-2 规范质量检查清单
 
|编号|检查项|自问 |
|---|---|---|
|1|目标明确|一个不了解项目背景的人，仅阅读“目标”部分，能否用一句话准确概括该项目的核心目的？ |
|2|范围有界|“不做什么”部分是否列出了至少三项明确排除的内容？ |
|3|验收可测|是否每一条验收标准都能转化为具体的自动化测试用例？ |
|4|性能有数|涉及性能的验收标准是否都包含可量化的具体数值指标？ |
|5|边界覆盖|是否定义了针对异常情况（如数据缺失、API故障、空输入等）的处理策略？ |
|6|无实现细节|规范中是否避免了“使用何种库”“代码如何组织”等实现层面的具体描述？ |
|7|术语一致|关键术语是否已明确定义，且全文表述是否保持一致？ |
|8|AI可执行|如果将这份规范交给一个从未参与过项目讨论的AI，它能否准确理解需要做什么、不做什么以及做到何种程度？ 
 
需要注意的是，第8条是最关键的检查项，也是检验规范质量的终极问题。规范的读者主要包括两类：同事与AI。如果一份规范能够让没有任何背景信息的AI准确理解任务目标、范围和验收标准，那么这份规范便是合格的。

这一章完成了 SDD 六阶段工作流的首要步骤 —— 将模糊的需求意图转化为结构化规范。
需求分析的核心任务并非 “穷尽所有功能”，而是促使隐含的决策显性化。每一个 “AI 可能产生误解或猜测的环节”，都应转化为 “人类
明确做出的选择”，包括数据来源、目标受众、实现程度以及排除范围。这些选择被记录在 proposal.md 中，成为后续所有开发工作的基石与验收标准。

proposal.md 遵循 “目标层（Why）→范围层（What）→验收层（Done）” 的三层结构，三者之间存在严密的逻辑约束关系：目标层界定范围层，范围层定义验收层，而验收层则反向验证目标层的实现程度。

撰写规范时，对精度的把控是一种需要刻意练习的核心能力：其标准在于 “恰好够 AI 执行”。关键在于将核心决策与约束写入规范，而将具体的实现细节留给 AI。判断这一界限的标准十分明确：如果某项决策改变了系统的行为，则必须写入规范；如果它仅改变代码的编写方式，则应交由 AI 决定。

在第 5 章中，我们将在 proposal.md 的基础上进行架构设计 —— 撰写 design.md，内容涵盖系统模型及接口契约。从界定 “做什么” 到 “怎么做”，这是信息密度最高的一次跨越。

**咖哥发言**
许多开发者习惯跳过需求分析直接着手设计，这无异于庖丁尚未看清牛的骨骼结构便贸然下刀，非刀不利，实乃不知从何处切入。投入 30min 撰写一份 proposal.md，后续能为你节省的绝不止 30min 的时间，更可能是长达三天的返工成本。此外，你规避的也不只是时间损耗，还有情绪上的无谓内耗：将心态从 “为何 AI 又生成了我不想要的结果” 的焦虑，转变为 “AI 严格遵守规范执行，一次到位” 的从容。
