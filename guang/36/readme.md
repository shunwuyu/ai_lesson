# Redis: 实现Agent 短期记忆存储的最佳方案

## 你了解 Agent Memory 吗？你是怎么设计的？

我觉得 Agent 的 Memory，本质上就是解决一个问题：**大模型（无状态）本身没有可靠的、跨请求的持久记忆能力，但是业务又希望它能够记住之前发生的事情，并且在后续对话中利用这些信息。**

所以我在设计 Memory 的时候，一般会把它分成短期记忆和长期记忆。

短期记忆主要解决当前会话的问题，比如用户前面说了什么、当前任务进行到哪一步了。这部分我倾向于用 Redis 存储，方便快速读取，也比较适合设置过期时间。

长期记忆主要解决跨会话的问题，比如用户的个人偏好、长期目标，以及历史交互中值得保留的信息。这部分我会考虑使用 Mem0 这样的记忆管理方案，负责记忆提取、更新和检索，底层再根据具体架构使用向量数据库或者其他存储。

另外还有一个非常重要的问题，就是上下文窗口有限。

如果我们每次都把完整的聊天记录塞给大模型，随着对话变长，不仅容易超出 Token 限制，还会增加推理成本和响应延迟。

所以我会结合上下文截断、历史总结和相关记忆检索。

简单来说，就是 Redis 管当前会话，Mem0 管跨会话的长期记忆，再通过总结和检索，把当前真正需要的信息组装成 Prompt，交给大模型。

## 上下文越来越长，你具体怎么处理？

很多候选人只会说一句：

> 超过 Token 限制就截断，然后对历史对话进行总结。

这个回答太浅了。

面试官更想知道的是：什么时候截断、截断什么、总结什么，以及如何避免丢失关键信息。

1. 推荐回答：截断、总结、检索三种策略

我不会简单地把历史消息从头开始截断，因为这样很容易丢失之前的重要信息。

我一般会结合三种策略。

第一种是截断。

对于比较早、而且价值比较低的普通对话，比如一些寒暄内容，可以优先移除。但我不会随便截断当前任务的关键约束、用户明确提出的要求，以及工具调用的必要结果。

第二种是总结。

当历史对话超过一定的 Token 阈值时，我会把较早的对话压缩成一份结构化的摘要。

比如用户的目标是什么、已经确认了哪些需求、做过哪些尝试、目前进展到哪里、还有哪些问题没有解决。

这样就算原始对话不再放进上下文，我们也能保留对当前任务有用的信息。

第三种是检索。

有些历史信息不适合直接总结，因为后续可能需要精确找回来。

例如用户之前提供的某个配置、错误日志，或者几轮对话之前确认的业务规则。这类信息可以保留在历史存储里，需要时通过关键词或者向量检索找回来。

所以我的思路是：**近期对话直接保留，较早的对话进行总结，历史细节按需检索。**

这样既能控制 Token 消耗，也能尽量减少上下文压缩带来的信息损失。

2. 真正落地时，如何设计上下文管理？

```
用户发送新消息
      |
      v
读取当前会话状态
      |
      v
读取近期聊天记录（Redis）
      |
      v
判断上下文 Token 是否接近预算上限
      |
      +---- 未超限 ----> 保留近期上下文
      |
      +---- 接近上限 --> 压缩较早的对话
      |                  更新会话摘要
      |
      v
从长期记忆中检索相关信息（Mem0）
      |
      v
组装最终 Prompt
      |
      v
调用 LLM / Agent
      |
      v
保存新消息、任务状态和必要的记忆更新
```

不能只根据消息条数判断是否需要总结，而应该根据 Token 数量、模型上下文窗口以及任务需要的预留空间来判断。

截断解决的是长度问题，总结解决的是信息压缩问题，检索解决的是信息按需取回的问题。

- 什么是负载均衡？

负载均衡就是把用户请求分给多台服务器，不让某一台扛太多压力，避免卡死，提升整体速度，一台挂了还能让别的顶上。
```json
http {
    upstream backend {
        ip_hash;  # 同用户固定一台
        server 192.168.1.10:8081;
        server 192.168.1.11:8082;
    }
    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

- 负载均衡算法
  - 轮询：请求挨个分给服务器；
  - 加权轮询：强的服务器多接点活；
  - 最少连接：挑现在活儿最少的；
  - IP 哈希：同一个用户，一直分到同一台机器。
    同一个用户始终连同一台服务器，会话数据存在这台机器上，不用跨机同步，保住登录状态。

- redis 高热频 读写优势？
Redis 是内存数据库，数据放内存里，读写速度极快，适合高频、高并发访问，能扛住大量热请求，比磁盘数据库（Mysql）响应快很多。

- 为什么会话闲置需要自动失效?

Redis 自带过期时间，会话存进去设好 TTL。用户很久不操作，时间到自动删掉这条会话，不用程序手动清理，节省空间，登录自动失效。

- 怎么理解redis的多实例共享？

多台 Redis 一起搭班子。主节点负责写数据，自动把数据同步给从节点，从节点可以用来读。
从节点可以用来读。集群模式下数据分开存在不同机器，客户端按规则去找，这样大家就能一起分担压力，扩容还能存更多数据。

- 分布式锁？

分布式锁就是多台服务抢同一个标记，抢到才能干活，防止多服务同时操作同一份数据，避免冲突。

多个服务操作同一个文件，用 Redis 分布式锁，保证同一时刻只有一个服务读写这个文件，防止内容写坏。
