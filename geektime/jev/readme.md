# Jev 决策模型工程实战
## 判断层为什么会成为 AI 应用的新基础设施？
2026 年 9 月 15 日，TypeSafe AI 发布了一个有点“怪”的模型，叫 Jev。
它不会聊天，不会写代码，一个字也不生成。你给它一段材料和几个事先定义好的问题，它只告诉你每个答案的概率。

就是这样一个“不会说话”的模型，发布 5 天就从排队申请变成了全面开放；Vercel、Netlify、Cloudflare、OpenRouter 这些开发者平台相继接入；不到十天，社区里基于它的项目就超过了 190 个。不到一个月，亚马逊云科技（AWS）开源了自己的同类模型，OpenAI 也推出了同类接口。这类只做判断、返回概率的模型，开始有了一个统一的名字：决策模型（Decision Model）。

三个问题：

第一，一个不会说话的模型，凭什么一下子就火了，还让大厂迅速跟进？
第二，它背后的“判断层”到底是什么，会不会像当年的数据库一样，成为 AI 应用绕不开的基础设施？
第三，如何快速学习这个模型，并为自己的工作所用？

## Jev 凭什么一下子火了？

先看看大家拿 Jev 做什么：工单分流、内容审核、反欺诈、模型路由，电商里的类目归属、属性抽取、假货识别，社区项目则集中在 Agent 安全护栏、邮件分拣和交易风控。这些事有一个共同点：过去几乎都是靠“让大模型输出 JSON”来做的。

所以 Jev 火的原因，用一句话总结就是：** 它治好了一个几乎每个 AI 应用都有的老毛病，用写作文的大模型去填选择题的答题卡。**

那这个毛病出在哪儿呢？我们来看一段似曾相识的代码。它在判断一条评论是不是投诉：调用大模型，从返回的文本里抠出 JSON，解析失败就重试，重试用完就返回默认值。

```python
import json
import re

# ❌ 错误示例：用生成文本的模型做判断，再依靠解析兜底
# 问题不在于实现细节，而在于这条路径需要持续增加兜底逻辑
# 抱怨
def is_complaint(review_text: str, max_retries: int = 3) -> bool:
    prompt = f"判断下面的评论是否在投诉，只输出 JSON：{{\"is_complaint\": true/false}}\n{review_text}"
    for _ in range(max_retries):
        raw = call_llm(prompt)  # 示意：调用任意一个大模型
        match = re.search(r"\{.*\}", raw, re.S)  # 模型可能在 JSON 前后附加说明文字
        if not match:
            continue
        try:
            data = json.loads(match.group(0))
        except json.JSONDecodeError:
            continue  # 可能缺少引号或多出逗号
        value = data.get("is_complaint")
        if isinstance(value, bool):
            return value
    return False  # 重试耗尽，只能返回一个默认值
```

这段代码写得并不差，但隐藏着三个毛病。就算我们要求 AI “写得更仔细”，问题还是无法根治。

第一是格式不可靠。大模型每一步都在整个词表里挑下一个字，“只输出 JSON”对它只是一条建议，它可能在前面加一句“好的，以下是结果”，也可能把字段名改成中文。结构化输出模式能保证 JSON 合法，却管不了取值对不对。TypeSafe 发布 Jev 时做过统计（见图 0-1）：受测大模型的结构化输出错误率从 0.58% 到 45.5% 不等。

第二是又慢又贵。“是不是投诉”只有两种答案，大模型却得把整段 JSON 一个字一个字写出来，推理模型还要先写一大段看不见的思考过程，这些都按更贵的输出计费。

第三最容易被忽略：你不知道它有几成把握。函数只返回 True 或 False，模型是十拿九稳还是几乎在随机猜测？你看不出来。让它顺便报个置信度也没用，同一条评论问两次，可能一次 0.9、一次 0.7，因为那个数只是它写出来的又一段文字，没有经过校准。

三个毛病，根子是同一个：大模型的接口是“文字进、文字出”，而判断需要的是“材料进、带概率的答案出”。Jev 恰好把这件事做对了。

## 判断层到底是什么？

有了前面的铺垫，判断层就好理解了。用一句话总结就是：判断层是代码和大模型之间，专门负责“做选择题”的那一层。

大模型相当于是问答题，它的输出通常是一大段文本，可能需要你从中提炼答案；判断层则是一张答题卡：选项是你事先印好的，它只能在选项里涂，每个选项旁边还标着有几成把握。

所以，判断层的接口至少要做到三点：答案范围由你来定；返回代码能直接用的值；每个答案都带着概率，让代码决定哪些自动处理、哪些交给人。

Jev 就是按这三点设计的。你给它一份输入状态，也就是要判断的材料，再给它一组问题。问题分三类：多选一（Choice）、等级打分（Score）和是非判断（Noul）。放到电商里，“这个商品属于服饰、数码还是家居”是多选一，“这条描述夸大宣传的程度是轻微、明显还是严重”是等级打分，“这两个商品是不是同一款”是是非判断。它们都是懂行的运营扫一眼就能判断的事，只是量太大，人看不过来，规则又写不全。

## 判断层放在系统的哪里？

有了判断层，AI 应用就形成了三层分工，这也是贯穿整门课的一句话：代码负责计算，Jev 负责判断，大模型负责推理和创作。

拿重复扣款来说。用户发来一句“同一笔订单被扣了两次钱，麻烦退一下”。代码先查扣款记录、核对金额和退款时效；再把用户消息、扣款记录和退款政策交给 Jev，一次问清：用户是不是在申请退款，扣款是不是真的重复，政策支不支持；代码根据答案决定退款，最后才让大模型写一段得体的回复。Jev 拿不准时，再转给人工客服。

你会发现，流程始终由代码掌控。Jev 只回答代码问它的问题，大模型只在需要文字时才需要调用。

## 判断层为什么会成为基础设施？

理解了判断层是什么，我们来回答开头的第二个问题。

不妨先回想一下数据库是怎么变成基础设施的：大家都通过 SQL 这个标准接口存取数据，底层换成哪家，应用基本不用改。一样东西能成为基础设施，通常有三个特征：接口标准，便宜到不假思索地调用，行为可以预期。这三个特征，判断层身上都已经冒头了。

先说接口。“输入状态加结构化问题”这种调用方式，已经不属于某一家公司了。OpenAI 的决策接口同样返回是非、多选一和打分三类带概率的答案；AWS 开源的决策模型也是在选项里作答、给出把握；开源社区还出现了和 Jev 请求格式一致的替代模型，改个服务地址就能切过去。

再说成本。Jev 只对输入计费，独立测试测出来它比前沿大模型便宜、快得多

最后说可预期。Jev 的设计者说过一句话：如果一个模型 95% 的时候能做对，却说不出自己什么时候落在那 5% 里，它就没法把这件事自动化。每天审核 100 万个商品，95% 的准确率意味着约 5 万个错判，业务方只能全部复核；但如果模型能把 80 万个标成“很有把握”，而这部分确实很少出错，人工就只需要看剩下的 20 万个。这个前提叫作校准：模型报出的概率要和实际正确率对得上。

有一点要分清：会成为基础设施的是决策模型这一类东西，不一定是发布 Jev 的这家公司。我的看法是，Jev 的护城河并不高。它发布时就宣布了 4000 万美元融资，可调用方式一公开，大厂几周内就拿出了同类产品。它最后能不能在商业上成为新的一极，现在谁也说不准；但大厂跟进得这么快，恰恰说明决策模型正在成为新的范式。就像数据库，最后留下的厂商不止一家，而会用数据库成了每个工程师的基本功。
