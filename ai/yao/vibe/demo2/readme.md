# Vibe Coding 开发前的步骤和关键点

通过vibe coding， 项目推的特别快， 但是越往后， 代码越乱 慢慢编程屎山。

越改越差， 最后牵一发而动全身， 整个项目直接崩盘。

问题在哪？ 不在于AI是强还是不强。

问题在于， vibe coding , 他并不是说， 我把这个活直接丢给AI , 就完事等他去
执行就可以了。 

而是你还是要构建一套工程流程， 去驾驭AI。

## Vibe Coding 标准工作流

### 开发前9个步骤， 打好地基。

#### 三个阶段

每个阶段都包含3个小步骤

1. 第一个阶段叫定图纸
- 先别去写代码， 先去导需求
就好像你去跟朋友聊天一样，把痛点，把目标用户， 把使用场景和你理想中的核心功能
全部都去讲给AI, 不用最求严谨，信息量， 定完需求。 
- 定完需求后， 把这个需求整理成一个PRD 的文档， 你来验收。
让Ai输出一份比较结构化的文档， 它中间包括了功能列表，包括用户流程，包括页面清单，
每个功能你都要补上一句， 到底做到什么时候才算完成？
比如登录成功， 他不是一句话， 要说清楚 登录失败提示是什么， 会不会锁定，
登录成功以后会调到哪里？
没有验收标准， AI会写的越来越发散。
- 提前订好视觉、和页面框架
找2-3个参考网站， 或者让AI 去给出几种风格的方案。
你要去决定， 我的导航栏怎么去放， 页面有哪些区别， 整体我想要的风格是简约
还是豪华风。
为了后面， 不让AI 一边去写功能， 一边去把UI 推导重来。
2. 第二个阶段打地基
- 明确项目的边界和非功能需求
  * 本地跑， 还是线上公开的，
  * 有没有用户的数据？ 支付、隐私合规
  * 性能和成本有没有上限。
  安全、性能、可用性、成本， 这四个非功能性需求不写清楚， 后面一定会返工。
- 锁定技术栈， 越可验证越好~
  并不是越主流越好， 而是越可验证越好。
  主流技术通常更稳。 资料多， 工具链成熟， AI也不容易瞎编。
- 让AI出轻量架构草案
  目录架构怎么分层
  核心模块有哪些
  数据模型长什么样
  有哪些组件

  可以持续迭代，但每次迭代， 都需要记录它的原因，

3. 第三个阶段立规矩
- 固化成文档
现在的Agent 和llm 交互都会用一个文档， 所以你需要把PRD、架构、当前状态
写成项目根目录的三个文本， 固化下来。
比如， PRD.md（产品需求文档） , ARCH.md （系统架构文档）， project.md（当前项目阶段）

做到哪一步， 有哪些已知问题， 下一步干嘛？

这三份， 就是AI的全局上下文， 重点就是每次大的改动， 这三份必须要是同步更新的。
否则Ai就会按旧的世界观去写新代码。

- 定开发规范和建参考资料夹
让AI 有照着抄的标准， 比如必须用TypeScript, 必须组件的命名规则， 然后文件大小上限。
建一个reference 这样的文件夹， 
放你认可的按钮、表单啊， 弹窗的标准实现， 
- 写代码前先拉git 和质量闸门。
  ai写的起飞了， 可以通过git 一键回溯到你以前的那个最好的代码。
  多分支开发， 能够做一个特性的并行开发，不用担心会有冲突。



### 开发中5个关键点

你负责边界和验收， AI负责体力活。

- 小步迭代， 端到端切片
坚持小步迭代的MVP 法则， 你不要让AI一口气去写一大堆。 而且一次只做一个可验证的小切片。
比如说从“页面能打开”， 到“能提交表单”， 到“服务端保存”， 到“权限校验”， 到“列表展示”
你只要没完成一个可以跑通的切片， 那就跑测试， 过lint, 然后Git 提交一次。 
- 主动拆分模块，禁止一坨代码。
- 禁止AI做主
你可用“状态摘要”去管理这个上下文， 你让它修一个按钮， 它可能顺便重写整个页面， 
每一次任务结尾， 加一句重要提示 只改我点名的文件和范围， 不要顺手重构， 不要去改UI 风格，
不要去改无关逻辑
- 死守安全底线， 
AI写代码往往只求能跑， 不会默认安全，
API 密匙不进前端, 很容易被人给hack 出来。
- 科学的应对报错。 
把错误信息给AI去修一次， 如果连续两次都没有新增一些证据呢, 那就停掉。
借助git , 回到上个稳定点。

## 总结

开发前的9个步骤讲了项目要去做什么， 怎么做，
开发中的5个关键点 决定项目能不能真正的去落地。

让我们一起顺利的去交互产品。
