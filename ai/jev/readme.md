# 火爆全网的Jev

非常非常特别的模型 Jev, 发布以后很快就在开发者圈里刷屏。

- Jev 准备去挑战ChatGPT \Claude 的全能模型？
- 它不就是个普通的分类器吗？

## Jev

1. Jev 到底是什么？
人的思考方式分成了两套系统：
系统一负责快速判断， 看到前面有东西飞过来， 我们可能本能会躲开。
看到一个人的表情，我们就能很快地判断他是否生气了。
而系统二呢： 负责的是慢思考， 
做一套复杂的数学题， 分析一份商业计划，或者权衡一个重要的决定， 都需要
投入更多的注意。
过去几年， 大模型的发展主要都在不断地加强系统二。
模型要学会去理解复杂问题，展开推理，调用工具，然后生成一段完整的答案。
而TypeSafe 提出问题就是一个AI系统里的每一步都需要这样的认真思考吗？
很多时候，程序需要的不是一篇文章， 而是一个判断，这就是Jev 出现的原因。

TypeSafe 把它叫做 System One Model  也就是系统一模型。
借鉴了思考，快与慢的概念。更多的是一种产品的类比，它并不是说复现了人的
直觉。而是专门去处理那些范围明确，需要快速完成判断的任务。

可以把Jev 理解成一个专门去给程序使用的决策模型。
传统大模型接受一段文字， 然后继续去生成文字，而Jev 接受一段材料和几个
提前定义的问题，返回的是选项，是分数和相应的概率， 

例子：

我买的东西一个星期还没到， 现在不想要了。
客服系统现在可能还不需要模型去写回复，而是需要搞清楚几件事。
这个用户是在查物流，还是在准备退款，情绪是不是激烈，要不要转给人工客服。
Jev 会从开发者给定的选项里做选择。并且告诉程序每个答案有多大概率。

程序拿到结果以后，就可以继续执行对应的流程。

总结：ChatGPT 负责写答案， Jev负责去判断。


2. Jev 能写代码吗？
它不能替你去写Python, 不能生成网页，也不能帮你写邮件或者营销文案。
它没有自由文本生成这个能力，但不代表他和编程没有关系。
一个编程Agent 在执行任务的时候， 要不断地判断下一步该读哪个文件，
该调用哪个工具，测试是不是通过， 要不要继续修改，Jev 不能生成代码，
但可以去参与这些流程里的选择。

他不是写代码的人， 更像是站在流程里面去做不断分流的人。

3. 为什么突然火了？

过去大家， 评价一个新的模型， 习惯会看他会不会写代码，数学能力有多强，
推理链到底有多长，而Jev 翻过去做了另一件事情，他主动放弃自由的文本生成，
只优化判断，优化选择，优化打分，好像在做一个减法，它正好集中了Agent正在
遇到的一个现实问题，我们经常会看到一个Agent, 最后生成了一份报告，好像
它只完成一次任务，但这个过程中它可能做了成千上百次的选择，比如说，
这条搜索结果有没有用？ 这两份资料是否在重复表达同一个观点？现在的信息够不够？
下一步应该调用工具，还是开始去写作， 这段结论有没有证据的支持？

如果每一次判断都需要去调用一次非常强的通用大模型， 延迟和成本会一层层累积。
更麻烦的是大模型明明只需要返回一个选项，但可能会顺手写一段解释，或者输出一个
不完全符合要求的JSON。 Jev 试图就是把这些小的判断单独拿出来解决。


4. 它的优势在哪里？
第一个优势就是快，按照TypeSafe 公开的信息， Jev处理一次决策通常需要70-500
毫秒，对于浏览器的操作，实时审核Agent路由，这类连续决策任务，这个差别会直接
影响到产品体验了（实时），
第二个优势就是便宜 官方价格， 每百万的token是 4.2 美分， 是ChatGPT 的1/10。

系统每天都要完成几十万次的判断，成本差距就会被无限的放大。
第三个优势是输出稳定， 如果开发者只给出了5个候选选项， 它就只会在
这五个选项里返回结果。 不会突然说创造出第6个答案。也不需要程序再从一段自然语言里
去提取结论，但这里一定要分清楚两件事情。

输出格式稳定不等于判断是一定正确的。Jev 不会再格式上胡乱发挥，但它可能在合法选项
里面去选错。所谓不产生自由文本幻觉， 解决的是接口问题，不是准确性的问题。

第四个优势它会返回概率， 普通分类器往往只会告诉你答案是什么， jev希望去把置信程度
也交给程序， 这样系统就可以设计不同的策略， 把握很高， 而且操作风险很低，可以自动执行。
把握一般，那就交给更强的大模型去做复核，把握太低了，或则涉及到退款、付款、删库这类
高风险动作，就转给人工。

Jev 可以读取一份材料同时回答多个相互独立的问题。
还是前面的客服消息，他可以同时判断用户意图、情绪、紧急程度和是否需要人工介入。

5. 这条技术路线到底成不成立
在它适合的任务里，这条路线肯定是成立的。
大语言模型通常要采用自回归生成，它需要一个token接着一个token 生成答案。
这个机制给了它写作， 编程和开放式推理的能力， 但程序只需要一个布尔值或者一个
枚举项，完整走一遍文本生成的流程，确实比较重，而Jev 把输出空间提前的限制住，
不再去生成任意文字，而是直接围绕着候选答案去计算概率，它失去了自由表达能力，
也因此换来了最低的延迟，更低的成本和更容易被代码处理的结果。

但它也不是所有问题的答案， 如果任务需要长链条推理，需要精确计算， 需要理解复杂的
日期关系，或者需要模型给出完整理由， Jev 都不是合适的选择。
我觉得不能问 Jev 和Claude 谁更聪明，他们解决的不是同一种问题

问题由开发者临时定义， 但输出必须限制在明确的类型和选项里，这一层以前经常交给大模型，
现在终于有人开始为它单独去设计模型了。

6. 开发者想用它来做什么？
开发者已经在尝试把Jev 放进不少的场景里面了。
像客服系统来判断用户意图， 把消息转到查询订单，退款投诉或者人工客服。
RAG 系统可以用它来判断检索回来的资料到底是不是相关的，先过滤掉无关内容，
再把剩下的材料交给llm。还可以用它来做垃圾信息， 辱骂内容风险文本的前置判断。

Agent可以用它来选择下一步调用哪个工具，或者决定任务是不是已经完成
Browser Use 社区做了一个 Jev Ultrafast 浏览器Agent 
jev 负责从网页元素，去选择该点击的按钮和输入框，只有需要真实需要填写文字的时候，
才去调用生成模型，一次苏黎世到伦敦的航班搜索演示， 只用了 7.1 秒。

TypeSafe 让Jev去玩游戏， 输入血量、敌人位置， 弹药数量等游戏状态，jev不断从
有限动作中去做选择，实现每秒的多次决策。

这些产品的共同点：任务边界清楚， 候选动作明确， 请求评率很高，程序不需要一段漂亮的
文字，只需要知道，下一步到底该做什么。

7. 如果想要试一试又该怎么去上手？
直接去用TypeSafe 提供的Playground 和 API ,
也可以通过Vercel AI Gateway 或者cloudflare 来调用。
一次请求里，可以放两个东西， 一份是state, 也就是模型做判断需要看到的材料，
另一份是questions, 也就是你希望它回答的问题， 候选选项或者评分范围，jev 
读完state以后， 会返回每个问题的答案和概率。程序根据概率去决定下一个动作，

真正困难的地方， 往往不是API的调通， 而是去把你的问题给定义清楚， 
还是那个问题 “我买的东西一个星期还没到， 现在不想要了。”
如果选项只有物流的延迟和申请退款，这道单选题本省就设计的不好，
物流的延迟是原因， 申请退款是诉求， 他们可以同时成立， 模型不会替开发者修复一套
混乱的业务标准， 给他的信息不完整， 问题不明确， 或者选项互相重叠，速度再快也没有
用， 所以比较稳妥的方法， 就是先选择一个范围很小， 答案比较清楚的任务， 拿一批已经
由人工处理的历史数据，让Jev 在旁边运行，暂时不要参加正式操作， 观察它在哪些任务上稳定，
置信度， 和真实正确率，是不是匹配，再更具风险设定自动通过，模型符合和人工处理的阀值。

低风险、高频，可测小的工作，可以更积极的去做自动化， 而退款、资金权限和删除数据， 任然保留代码规则
和人工审核。

jev真正有意思的地方，不只是说把原本一次调用做便宜了， 让原本因为成本太高，而没有发生的判断开始大量出现，
当然更多地判断不一定带来更好的结果， 如果标准本身就错了， 系统只是在更快、更便宜的重复错误，

我始终认为， Jev 至少提出了一个很值得观察的方向，未来的软件未必需要一个模型包办
所有事情，复杂推理可以交给强模型， 内容生成可以交给生成模型， 范围明确的小判断，
再去交给Jev 一类的决策模型。再配合代码规则和人工审核，不是每一道题目都需要写一篇作文
有些时候程序要真正需要的只是一个足够快，带着概率可以立刻执行的答案。
