2. 你们项目里 Agent 的任务状态存在哪，中断后怎么恢复

3. LangChain 里 Tool、Memory、Chain、Graph 分别解决什么问题
> 回答思路
> 先逐个解释每个组件定位、解决的痛点；然后讲演进关系：Chain 是早期线性编排 → Graph（LangGraph）是现代 Agent 非线性编排；最后拿一个「订单> 查询 Agent」完整串一遍，收尾点清楚边界和踩坑点

- Tool（工具）
给大模型外接能力，弥补 LLM 本身的知识盲区、无法执行外部操作的短板。
解决问题：
LLM 本身只有训练截止前的静态知识，不能联网、查数据库、调用接口、执行代码、操作业务系统。Tool 就是把外部能力封装成标准化、模型能看懂的函数，包含：工具名称、描述、入参 JSON Schema、实际执行逻辑。

- 模型通过 Function Calling 识别什么时候该调用哪个 Tool，自动生成参数
- 工具负责和外部系统交互（查订单、查天气、数据库查询、发邮件），返回结果给 LLM
- MCP 是 AI 领域的“USB-C 标准协议”，把工具、资源、提示词统一成可跨应用复用的接口，解决“每个模型都要单独接一遍工具”的问题。

> 
> 注意区分：Tool 只负责**单次能力调用**，它不做流程控制、不存历史、不知道下一步该干嘛。

- Memory（记忆）
**句话定位：给 Agent 提供上下文存储，解决大模型无状态、记不住多轮对话历史的问题**
解决问题：
原生 LLM 每次调用都是独立请求，没有记忆。Memory 负责管理会话上下文，分好几类：

- 短期记忆：会话内对话历史（ChatMessageHistory），同一次对话记住前面用户提问、工具返回、模型回答；
- 窗口记忆、摘要记忆：防止上下文无限膨胀，自动截断或者摘要压缩历史；
- 长期记忆：向量记忆，跨会话持久存储用户信息、业务知识（RAG 也常和它搭配）。

> 
> 重点：Memory 只负责**存取上下文**，它不决定流程怎么走、什么时候调用工具。LangChain 的 Memory 都是解耦组件，可以插拔。

- ### Chain（链，LangChain 早期编排原语）

**一句话定位：线性、固定顺序的任务编排，把 LLM、Prompt、Tool、RAG 等组件串成一条流水线**
解决问题：
早期简单任务，流程是固定单向的：输入 → A 环节 → B 环节 → 输出，没有循环、没有分支判断。
举个典型 RAG Chain：用户 query → 检索向量库 → 把检索文档 + 问题塞 Prompt → LLM 生成回答。

- 特点：**顺序固定，单向执行，不能回头、不能循环、不能动态分支**；
- 短板：不适合 Agent！Agent 经常需要：调用工具拿到结果之后，再判断要不要继续调用工具、要不要追问用户，Chain 做不到这种动态循环。

> 
> 面试加分：Chain 适合确定性流水线（RAG 问答、固定模板摘要），**不适合自主规划式 Agent**，这也是后面 LangGraph 诞生的原因。

- ### Graph（LangGraph，现在 LangChain 生态做 Agent 的核心）

**一句话定位：有状态、支持循环、分支、条件跳转的图编排框架，专门用来做自主 Agent 的执行流**
解决问题：
弥补 Chain 线性固定流程的缺陷。Agent 是闭环：思考→选工具→执行工具→拿到结果→再思考，可能循环多轮，也可能根据结果走不同分支，甚至暂停等待人工审批。
LangGraph 核心能力：

1. 状态（State）贯穿整个图，状态里放消息列表、工具返回、中间变量；
2. 节点（Node）：执行单元（比如调用 LLM 思考节点、调用 Tool 节点）；
3. 条件边：根据节点返回结果动态路由，判断 “继续调用工具” 还是 “直接回答用户”；
4. 支持中断、断点恢复、持久化状态，正好对上刚才你上一题问的 Agent 任务中断恢复。

> 
> 关键区分：Chain = 固定流水线；Graph = 动态自主闭环，是现在工业界 Agent 的主流方案。

- 实战串联：订单查询 Agent（业务场景，面试直接讲这个例子，非常加分）

场景：用户提问：“帮我查一下昨天下单的快递到哪了，如果已经签收，把签收照片发给我”
我们把四个组件全部串起来，讲清楚流转：

1. **Memory（记忆）**
用户发起对话，Memory 加载本次会话的历史消息，把用户这句话追加到消息列表，存入会话状态；如果是多轮对话，还记得用户之前说的手机号、订单号。

> 
> Memory 提供整个 Agent 的上下文原料。

2. **Graph（LangGraph 主控编排框架）**
整个 Agent 的闭环流程由 Graph 定义，Graph 的 State（状态）里承载 Memory 消息、工具返回结果、订单信息；图里定义 2 个核心 Node：

- node1：LLM 思考节点（模型决策）
- node2：Tool 调用节点
条件路由规则：LLM 输出要调用工具 → 走到 Tool 节点；LLM 判断信息足够不用工具 → 直接结束图、返回回答。

3. **Tool（业务工具）**
我们预先封装 2 个 Tool：

- `query_order_logistics`：传入订单号，调用后端订单接口，查物流状态
- `get_sign_photo`：传入订单号，获取签收图片链接

4. **完整流转链路：**
① 用户输入问题 → Graph 初始化 / 加载 State，Memory 把历史消息塞进 State；
② Graph 走到【LLM 思考 Node】：LLM 看到用户问题，判断需要先查物流，调用`query_order_logistics`这个 Tool，输出调用参数；
③ 条件边判定：要调用工具 → 路由到【Tool Node】；
④ Tool 执行，调用业务接口拿到物流结果：【订单已签收】，返回结果；
⑤ Tool 结果写回 Graph 的 State，同时这条工具消息存入 Memory；
⑥ 回到 LLM 思考 Node（Graph 支持循环！这是 Chain 做不到的）：LLM 看到返回结果是已签收，判断还需要调用第二个 Tool `get_sign_photo`；
⑦ 再次路由到 Tool 节点，拿到图片链接，写入状态和 Memory；
⑧ LLM 再次思考：信息全部齐全，不需要再调用任何工具；条件路由走【结束分支】；
⑨ LLM 整合所有信息，生成最终回答返回用户；本轮所有对话、工具交互记录持续保存在 Memory 里。

## 手撕算法：二叉树的层序遍历，并要求按层输出结果

前序、中序、后序遍历都属于深度优先， 它们的共同点都是“一条路走到底”

层序遍历的核心是使用队列（Queue）来实现广度优先搜索。

1. 初始化一个队列，将根节点入队。
2. 当队列不为空时，记录当前队列长度 size，这个 size 就是当前层的节点数量。
3. 循环 size 次，依次出队节点，将其值加入当前层结果列表，并将其左右子节点（若存在）入队。
4. 每处理完一层（即内层循环结束），将该层结果列表加入最终结果集。
5. 重复直到队列为空。


```
var levelOrder = function(root) {
    if (!root) return [];

    const queue = [root];
    const result = []; // 初始化一个一维数组

    while (queue.length > 0) {
        // 注意：这里依然需要记录 size，用来控制出队次数和子节点入队时机
        const levelSize = queue.length; 

        for (let i = 0; i < levelSize; i++) {
            const currentNode = queue.shift();
            result.push(currentNode.val); // 直接将节点值放入扁平数组

            if (currentNode.left) queue.push(currentNode.left);
            if (currentNode.right) queue.push(currentNode.right);
        }
    }

    return result; // 最终返回如: [3, 9, 20, 15, 7]
};
```

  为什么要三次握手？
  TCP 三次握手，本质是为了确认双方收发能力正常，并同步初始序列号。

![](https://gips2.baidu.com/it/u=3898048210,2100993062&fm=3074&app=3074&f=JPEG?w=751&h=534&type=normal&func=)

seq 是 Sequence Number，也就是序列号。 
给每个要发送的数据字节编的“身份证号”，这样接收方收到数据后，才能按顺序排好，或者发现哪个“号”丢了，要求重传。

第一次握手（建立连接请求）：
客户端发送一个 SYN=1 的包，携带初始序列号 seq=x，进入 SYN_SENT 状态。
第二次握手（确认请求并同步序列号）：
服务端收到后，回复一个 ACK=1, SYN=1 的包。它确认客户端的序列号（ack=x+1），并携带自己的初始序列号 seq=y，进入 SYN_RCVD 状态。
第三次握手（最终确认）：
客户端收到回复，发送 ACK=1 的包，确认服务端的序列号（ack=y+1），进入 ESTABLISHED 状态。服务端收到此包后，也进入 ESTABLISHED 状态，连接正式建立。
